# HigGym

Apple HIG · SwiftUI(iOS 26) 컴포넌트를 목차별로 뜯어보는 주석 노트.
각 항목마다 **WHEN**(언제·어떤 기준) · **WHY**(왜 이런 설계·기본값) · **TIP**(실무 참고)을 답니다.

## 📱 실습 앱 (iOS 26)

문서를 읽는 데서 그치지 않고 **직접 만져보고 퀴즈로 확인하는 교구**를 iOS 앱으로 만들었습니다.

앱의 근간은 **문서에 있는 프리뷰 목업 그대로**입니다. `toolbar-annotated.html`의 `<figure class="preview">` 를 노드 트리로 추출해 SwiftUI로 다시 그리므로, 문서에서 본 그림과 앱의 그림이 같습니다. 그 그림이 설명의 시작점이자 손으로 만지는 대상이 됩니다 — **부위를 누르면 그 자리가 무엇을 말하는지** 알려주고, 실습에서는 설정을 바꿀 때마다 같은 그림이 다시 그려집니다. 그림으로 배치를 잡은 뒤에는 실제 SwiftUI API로 렌더링한 전체 화면과 대조할 수 있습니다.

```bash
cd HigGymApp
xcodegen generate          # project.yml → HigGym.xcodeproj
open HigGym.xcodeproj      # 또는 아래 명령으로 시뮬레이터에 바로 설치
xcodebuild -project HigGym.xcodeproj -scheme HigGym \
  -sdk iphonesimulator -destination 'platform=iOS Simulator,name=iPhone 17 Pro' build
```

### 학습 — 여덟 편의 워크북

앱의 첫 화면은 목록이 아니라 **코스**입니다. 한 편이 결정 하나를 다루고, 다섯 단계를 순서대로 밟습니다.

1. **써보기** — 표본 앱(노트)을 실제 크기로 띄우고 과제를 줍니다. *"노트를 하나 지워 보세요. 툴바에는 삭제가 없습니다."*
2. **적어보기** — 답을 보기 전에 씁니다. 무엇을 느꼈는지, 손이 어디로 갔는지. 먼저 답을 보면 "알고 있었다"고 느끼고 지나가기 때문에 순서를 이렇게 뒀습니다.
3. **이유 확인** — 내가 쓴 글과 기준을 나란히 놓습니다. 이 앱이 한 결정 · 왜 그렇게 했나 · 뒤집으면 어떻게 되나 + 근거 항목.
4. **비교** — 어긴 화면과 고친 화면을 **같은 자리에서 즉시 갈아 끼웁니다**. 두 화면을 나란히 놓으면 각각이 절반으로 줄어 정작 봐야 할 것이 사라지므로, 전체 크기 한 화면을 위에서 바꿉니다. 둘 다 살아 있어 오가도 스크롤 위치가 유지되고, 바뀌는 자리에는 테두리가 켜집니다.
5. **배운 것 적기** — 다음에 꺼내 쓸 문장으로 남깁니다. **노트** 탭에 쌓이고, 통째로 복사해 밖으로 가져갈 수 있습니다.

여덟 편이 다루는 화면은 전부 같은 앱 한 벌입니다. 결정 하나만 뒤집어 같은 앱이 어떻게 나빠지는지 봅니다.

탭은 셋입니다 — **학습**(코스) · **노트**(내가 쓴 글) · **자료**(항목 68 · 실수 100 · 원칙 7 · 실습 5 · 퀴즈). 아래 자료들은 없앤 게 아니라 뒤로 물린 것이고, 레슨 안에서 **근거 본문**은 바로 열립니다.

### 항목 — 68개를 그림으로 훑기

챕터·섹션별로 목업 썸네일이 먼저 보이고, 항목을 열면 큰 그림과 함께 WHEN·WHY·TIP·적절한 예·잘못된 예가 붙습니다. 그림의 툴바·캡슐·탭바·시트·배지 같은 부위를 누르면 그 자리의 문법과 근거 항목 번호가 나옵니다.

### 예제 보기 — 그림과 똑같이 생긴, 실제로 동작하는 화면

항목마다 **예제 보기**가 있습니다. 목업이 배치를 그림으로 읽게 해준다면, 예제는 같은 배치를 **진짜 SwiftUI API로 세운 전체 화면**입니다 — 눌러보고 스크롤해봐야만 알 수 있는 것을 손에 남기기 위해서입니다.

- 툴바 아이템을 하나씩 늘리다 보면 **시스템이 나머지를 … 로 접는 순간**을 직접 만납니다 (1.1.7)
- 대형 제목이 스크롤에 따라 접히고, `inlineLarge`는 접히지 않는다는 차이를 같은 목록에서 비교합니다 (1.2.1 · 1.2.2)
- 검색은 자리만 다를 뿐 **전부 실제로 걸러집니다** — 하단 캡슐과 상단 서랍의 손 동선 차이가 그대로 느껴집니다 (1.4)
- 가장자리 효과·재료는 화면 안에서 **배경(어두운 단색 · 사진 · 흰색)을 바꿔가며** 판정합니다 (1.3 · 6.1)
- 텍스트는 폭 슬라이더와 Dynamic Type 조절이 붙어 있어, 잘림·축소가 언제 일어나는지 스스로 만듭니다 (2.1 · 2.2)
- 배지는 항목을 읽으면 실제로 줄고, 시트는 detent에 걸리며, zoom 전환은 누른 카드에서 열립니다 (3 · 4)
- 8장 **원칙 7개**는 스위치 하나로 같은 화면을 어긴 구성 ↔ 지킨 구성으로 뒤집어 비교합니다

예제를 처음 열면 **해보세요** 안내가 비모달 시트로 뜹니다(4.1.5 그 동작입니다) — 읽으면서 뒤 화면을 그대로 만질 수 있고, 이 화면을 만든 SwiftUI 코드와 그 항목의 WHEN·WHY가 함께 붙습니다. 화면 가장자리의 작은 캡슐로 언제든 닫거나 안내를 다시 열 수 있습니다.

### 실수 100 — 직접 밟아봐야 안 밟는다

본문 68개 항목의 **잘못된 예 154개**를 실수 단위로 병합·선별해 **100편**으로 묶었습니다. 항목이 "이건 이렇게 생겼다"라면, 실수는 **"이렇게 하다 밟았다"**입니다.

실수 한 편은 이렇게 구성됩니다.

1. **무엇을 했나** — 실수 한 줄 (예: *성격이 다른 액션을 한 캡슐에 묶는다*)
2. **그때는 왜 그게 맞아 보였나** — 회고의 핵심. 이게 없으면 남의 잘못을 지적하는 목록에 그칩니다
3. **판단 기준** — 8장 원칙에서 가져온 한 문장 (원칙 번호 표시)
4. **고치면** — 고친 뒤의 모습
5. **직접 해보기** — 그 실수를 만들 수 있는 **동작하는 예제 화면**
6. **근거** — 본문 항목으로 바로 이동 + Apple HIG·WWDC 출처

분류는 8장 원칙 7개를 그대로 척추로 쓰고 원칙에 안 걸리는 "구조" 하나를 더한 8개이며, 심각도는 *자주 밟는다 · 사고로 이어진다 · 놓치기 쉽다* 3단입니다. 겪어본 실수를 체크해 100편의 진행도를 볼 수 있고, 항목 상세에는 **"여기서 나온 실수 N개"** 역방향 링크가 붙어 항목과 실수가 서로를 가리킵니다.

100편이 근거로 삼은 본문 항목은 **75개 중 75개** — 문서 전체를 덮습니다.

#### 전용 예제 — 실수한 화면과 고친 화면을 나란히

10편에는 **그 실수만을 위한 예제**가 붙어 있습니다. 한 화면에 미니 아이폰 두 대를 세우고 왼쪽엔 *이렇게 했다*, 오른쪽엔 *이렇게 고쳤다* 를 동시에 띄웁니다. 번갈아 보여주는 토글이 아닌 이유는, 배워야 할 것이 각각의 화면이 아니라 **둘 사이의 간격**이기 때문입니다.

두 화면 모두 진짜로 동작합니다 — 왼쪽에서 삭제를 눌러 지워보고 오른쪽에서 스와이프로 지워보며 지운 개수를 비교하거나, Dynamic Type 슬라이더 하나로 두 화면을 함께 키워 어느 쪽이 먼저 무너지는지 볼 수 있습니다. 좁으면 `크게 보기`로 실제 크기에서 만집니다.

#### 회고 — 어쩌다 그렇게 됐는가

`Retrospectives/*.md` 에 회고를 씁니다. 카드의 세 줄이 요약이라면 회고는 그 세 줄이 나온 과정입니다.

> **증상** → **그때는 왜 그게 맞아 보였나** → **무엇이 부러졌나** → **기준** → **고친 뒤** → **남는 것**

두 번째 절이 이 시리즈의 핵심입니다. 그게 없으면 남의 잘못을 지적하는 목록에 그칩니다. 마크다운이 원본이라 그대로 발행할 수 있고, `build_mistakes.py` 가 절 단위로 잘라 앱에도 싣습니다.

지금은 **전용 예제 10편 · 회고 11편**이 준비돼 있습니다(목록에서 `회고 있는 것만` 으로 추릴 수 있습니다). 나머지는 같은 틀로 채워 나갑니다.

```bash
python3 Tools/build_mistakes.py   # mistakes_data.py + entries.json → mistakes.json
```

실수 문장(무엇을·왜·고치면)은 [`Tools/mistakes_data.py`](./Tools/mistakes_data.py)에 직접 쓰고, 기준·근거·예제 연결은 문서에서 조인합니다. 본편 100편 외에 예비 19편이 같은 파일에 있어 `spare` 플래그만 옮기면 교체됩니다.

### 실습실 — 라이브 목업 + 실제 화면

| 실습 | 무엇을 만지는가 | 본문 |
|---|---|---|
| 툴바 배치 실험실 | leading·principal·trailing·bottom에 아이템을 넣고 제목 표시 방식·검색 배치를 바꾼다 | 1.1 · 1.2 · 1.4 · 7.1 |
| 스크롤 엣지 이펙트 | soft/hard/hidden × 단색·사진·흰 배경 × 두꺼운 material | 1.3 · 6.1 |
| 텍스트 잘림·축소 | lineLimit · truncationMode · minimumScaleFactor · reservesSpace · Dynamic Type · FormatStyle 로케일 | 2.1 · 2.2 |
| 탭바 구성 | 탭 개수 · 배지 · `role: .search` · minimize · bottom accessory · 상세에서 숨김 | 3.1~3.5 |
| 시트 디텐트 | large/medium/custom/combo · 그랩바 · 비모달 · zoom 전환 · full cover | 4.1~4.3 |

툴바·탭바 실습은 설정을 바꿀 때마다 **문서와 같은 목업**이 즉시 다시 그려지고, 그 아래 **실시간 판정**이 붙습니다 — 지금 구성이 어떤 기준을 지키고 어기는지, 근거가 되는 본문 항목 번호와 함께. 각 실습에는 그 구성에 해당하는 SwiftUI 코드도 생성됩니다.

### 실전 — 화면으로 판단하기

문장을 읽고 고르는 것과 **화면을 보고 고르는 것**은 다른 근육입니다. 실무에서 판단하는 대상은 언제나 화면이므로, 퀴즈 탭 맨 위에 화면으로 하는 훈련을 뒀습니다.

**샘플 앱 뜯어보기** — 실제로 쓸 수 있는 노트 앱 한 벌입니다. 열고, 쓰고, 밀어서 지우고, 검색해 보세요. 그다음 결정 8개를 하나씩 누르면 **그 자리에 테두리가 켜지고** 무엇을·왜 그렇게 했는지, 뒤집으면 어떤 실수가 되는지가 근거 항목과 함께 붙습니다. 안내는 비모달 시트라 읽으면서 앱을 그대로 만질 수 있습니다.

**이 기준이면 어느 화면 (8문항)** — 기준 한 줄을 주고 **돌아가는 화면 두 개** 중에서 고릅니다. 두 화면은 같은 앱이고 결정 하나만 다릅니다. 고르기 전에 직접 만져볼 수 있고(본문을 길게 눌러보거나, 행을 밀어보거나), 고른 뒤에는 각 화면 아래에 왜 맞고 왜 틀렸는지가 붙습니다.

**이 화면, 왜 이렇게 했나 (6문항)** — 화면을 보고 그 배치의 이유를 고릅니다. 오답 보기도 그럴듯한 것들이라("가장 중요한 기능이라 잘 보이는 자리에 뒀다") 기준을 정확히 알아야 갈립니다.

해설에는 근거 항목 번호와 **관련 실수 번호**가 함께 붙어, 실전 → 항목 → 실수·회고로 이어집니다.

### 퀴즈 — 396문항

- **판별**: 본문 68개 항목의 적절한 예·잘못된 예를 보고 즉시 판단
- **선택**: WHEN(이 상황) → 어떤 컴포넌트를 쓰는가 — 보기가 **네 개의 목업 그림**이라 라벨이 아니라 배치를 읽어야 풀립니다
- **원칙**: 잘못된 설계가 8장 원칙 7개 중 무엇을 어겼는가
- **실무**: 직접 작성한 시나리오 객관식

해설에는 언제나 본문 항목 번호가 붙고, 관련 실습으로 바로 넘어갈 수 있습니다. 틀린 문제는 오답 복습에 모입니다.

### 콘텐츠는 문서가 원본입니다

앱이 쓰는 데이터는 `toolbar-annotated.html`에서 뽑아냅니다. 문서를 고친 뒤 아래를 다시 실행하면 앱 콘텐츠와 자동 생성 문항이 함께 갱신됩니다.

```bash
python3 Tools/extract_content.py   # → HigGymApp/Resources/entries.json
```

### 라이트 · 다크

앱은 시스템 모드를 따라갑니다. 팔레트 12색이 모드별 짝을 갖고 있고, 라이트 팔레트는 다크를 뒤집은 것이 아니라 **흰 배경에서 대비가 서는 값**을 따로 골랐습니다 — 강조색은 한 단계 진합니다(8.1.4 가독성 > 미학).

예제는 시스템 컴포넌트로 만들었으므로 모드를 그대로 따라갑니다. 다만 **판정 조건이 되는 배경**(스크롤 엣지·재료 실습의 단색/사진/흰 배경)은 앱 모드와 무관하게 고정입니다. 조건이 흔들리면 세 배경의 비교 자체가 성립하지 않기 때문입니다. 문서의 목업 폰 그림도 다크 일러스트 그대로 둡니다.

문서(`toolbar-annotated.html`)는 아직 다크 전용입니다.

## 🌐 언어 / Language

한국어와 영어를 모두 지원합니다. 오른쪽 위 **한국어 · EN** 토글로 전환하거나, URL에 `?lang=en`(영어) / `?lang=ko`(한국어)를 붙여 바로 열 수 있습니다. 선택한 언어는 브라우저에 저장되며, 기본값은 한국어입니다.

Available in Korean and English. Use the **한국어 · EN** toggle at the top right, or open a URL with `?lang=en` / `?lang=ko`. Your choice is remembered in the browser; the default is Korean. All English strings live in [`i18n-en.js`](./i18n-en.js) — the Korean text stays in the HTML and is swapped in place at runtime.
